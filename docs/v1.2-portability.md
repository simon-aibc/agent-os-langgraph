# v1.2 Backend portability

## Goal

Lift the current hard-wired Claude Code and Codex CLI branching in agent_os/cli_backends.py into a BackendAdapter registry that new adapters can plug into, so switching provider does not require graph or dispatcher changes.

## Motivation

- v1.1 shipped two hard-coded CLI backends for Claude Code and Codex.
- Antigravity is a candidate backend, but it must be gated on stable noninteractive output and enforceable permission modes.
- Operators need a health check that reports installed binaries, authentication state, and configured roles before a workflow starts.
- Operators need named profiles instead of ad-hoc environment exports for common router, architect, executor, and sandbox combinations.
- Backend selection must be visible and durable enough to make resume behavior predictable.

## In scope

- Introduce a BackendAdapter registry so architect and executor roles can target additional CLI or API providers without touching graph code.
- Add an agent-os doctor command that reports installed binaries, authentication status, and configured roles in a machine-readable format.
- Support named configuration profiles that select router, architect, executor, and sandbox defaults in one switch.
- Add ROUTER_MODE=direct-escalation to bypass Tier-2 structured routing when the operator has already chosen an architect-first workflow.
- Persist the resolved backend selection inside the SQLite checkpoint so a resumed thread continues on the same provider it started with.
- Add a candidate Antigravity CLI adapter behind the registry once its noninteractive output and permission contract can be enforced.

## Out of scope

- Skill packages remain v1.3 scope.
- The Hermes bridge remains v1.3 scope.
- Vault memory remains v1.4 scope.
- Context profiles remain v1.5 scope.
- REPL and TUI interfaces remain v1.6 scope.
- Ambient interfaces remain v2.0 scope.
- OS-level isolation remains v2.1 deployment territory.

## Contracts

### BackendAdapter interface

Define a small adapter boundary for every provider that can serve a graph role. The existing CLI runner logic in agent_os/cli_backends.py becomes the reference adapter implementation for Claude Code and Codex.

```python
class BackendAdapter(Protocol):
    name: str
    supported_roles: set[Literal["architect", "executor", "router"]]

    def invoke(
        self,
        brief: str,
        sandbox_root: Path,
        timeout: float,
    ) -> object: ...

    def authentication_status(self) -> AuthStatus: ...

    def forbidden_arg_set(self) -> set[str]: ...
```

Register adapters by backend name and role. Resolve a backend by role plus name string, matching the existing LLM_ARCHITECT=cli/claude-code and LLM_EXECUTOR=cli/codex convention. Keep graph nodes and dispatcher code dependent on the registry contract, not provider-specific branches.

### agent-os doctor

Add a command that reports whether the local installation can run the configured backend graph. Output must support both machine-readable JSON and a human-readable summary table.

```bash
agent-os doctor --json
```

Include these fields in the doctor report:

- Registered adapters and their supported roles.
- PATH resolution for each required binary.
- authentication_status() result for each adapter, with secrets and tokens redacted.
- Active profile name, if any.
- Resolved router, architect, executor, and sandbox.
- checkpoints.db reachability.
- Warnings for missing or misconfigured items.

Return exit code 0 when the configuration is healthy. Return exit code 1 when any required check fails.

### Config profiles

Use named profiles to switch router, architect, executor, and sandbox in one flag. Read profiles from $XDG_CONFIG_HOME/agent-os/profiles.toml, with fallback to ~/.config/agent-os/profiles.toml.

```toml
[profile.local]
router = "ollama/llama3.1"
architect = "cli/claude-code"
executor = "cli/codex"
sandbox = "./sandbox"
description = "Local router with subscription CLI agents"
```

Profile entries use [profile.<name>] with router, architect, executor, sandbox, and description keys. Resolve profile selection in this order:

- --profile CLI flag.
- AGENT_OS_PROFILE environment variable.
- Default profile marked in the file.
- Current environment-variable behavior.

Keep current environment-variable behavior backward compatible. Never store secrets in profiles.

#### Profile inheritance

Support one-level profile inheritance in v1.2 with an extends key inside [profile.<name>]. The child inherits every key from the parent; keys defined on the child override the parent's value. Keep inheritance single-parent and one level deep. Do not implement diamond resolution.

```toml
[profile.cli-base]
router = "ollama/llama3.1"
architect = "cli/claude-code"
executor = "cli/codex"
sandbox = "./sandbox"

[profile.cli-write]
extends = "cli-base"
sandbox = "./worktree-sandbox"
```

- Circular extends chains fail loading with a clear error.

### ROUTER_MODE=direct-escalation

Add direct-escalation as a new value for the existing ROUTER_MODE environment variable. In direct-escalation mode, skip Tier-2 structured routing entirely; every task that misses Tier 1 goes straight to architect.

In direct-escalation mode, transient router-call retries are disabled. The mode already commits to skipping structured routing; retrying adds no value. Cascade mode retry behavior is unchanged.

Use this mode for operators who have already decided on an architect-first workflow, typical for a CLI Architect plus CLI Executor loop. Avoid spending a model call on structured routing when the operator wants escalation anyway.

Keep cascade as the default router mode. Ensure direct-escalation still respects human_gate; architect plans must still pause for approval before executor work starts.

### Checkpoint backend persistence

Write the resolved backend selection into SimonState at graph start and preserve it through the SQLite checkpointer. On --resume, read the persisted selection and reject a conflicting environment override with a clear error instead of silently switching providers mid-thread.

By default, fail on a conflicting environment override at resume. Name the persisted binding and the conflicting override in the error. Recommend either editing the environment or profile to match, or passing --force-rebind.

Accept --force-rebind at the CLI. When set, emit a warning line naming the previous and new binding, update the persisted binding, then continue resume. Always emit this warning; never silence it.

Use this state key:

```python
state["backend_binding"] : BackendBinding
```

Define BackendBinding as a Pydantic model with router, architect, executor, and profile_name fields. Store provider names and role bindings, not credentials.

### Antigravity adapter (candidate)

Keep the Antigravity adapter behind the registry and opt-in only. Gate support on both acceptance criteria:

- A documented noninteractive invocation form with parseable output.
- A permission mode the runner can pin equivalent to Claude plan and acceptEdits or Codex read-only and workspace-write.

Until both criteria are documented by the vendor, ship the adapter as a stub that returns a clear "not yet supported" error. Match the roadmap position that Antigravity is a candidate, not a supported backend.

List the Antigravity adapter in agent-os doctor with status "not-yet-supported". Include a short actionable message that names the two acceptance criteria: noninteractive form and enforceable permission mode. Point operators to docs/roadmap.md v1.2 or the adapter module docstring for updates.

When invoked directly, the stub returns the same "not yet supported" error and lists the acceptance criteria.
